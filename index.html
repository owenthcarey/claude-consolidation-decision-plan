01 / The sequence

Take the free savings before buying software.

The initial plan jumped from sixty accounts to a presumed seat map and bot. The revised plan inserts the missing counterfactual: cancel and downgrade first, then decide whether any problem remains worth automating.

03 / Conditional architecture

If the gate passes, use two lanes.

Direct users get the least expensive named seat that meets measured demand. Occasional users can submit bounded work through Teams—but only after a pilot proves that the API and automation economics work.

Supported base case

Claude Platform API

Scoped credentials, rate and spend controls, predictable attribution, and a supported path for multi-user production automation.

Excluded without written approval

One pooled Premium seat

A named member, one finite usage pool, shared identity, lost attribution, and a brittle dependency for the whole service.

05 / Management inputs

Six facts before one build decision.

Headcount is not usage. Management needs a billing and workflow inventory before the seat map, API budget, or ROI can be stated responsibly.

Actual plan, invoice, billing interval, usage-credit purchases, and renewal commitment for all sixty accounts.
At least ninety days of active-use and limit-hit evidence for every employee.
Workflows that genuinely require direct Claude access rather than occasional task submission.
Fully loaded build cost plus monthly hosting, maintenance, support, and ownership.
Management's required payback period—recommended decision window: twelve to eighteen months.
The actual objective: subscription savings, automation productivity, broader access, or a measured combination.
